# Календарь: модуль Freedom `calendar` (проект)

Черновик 0.2 от 2026-11-23 (0.1 — 22.11). Кода нет; начинаем после почты (решение владельца 22.11).
Готово в ядре и модулях на 23.11: общий вход `provider-accounts`, общий почтальон `home-relay`, действия
приложений для агента F14b-1 (`provides.actions`, `app_list`/`app_action`).
Связанные документы: SPEC Freedom §3.6 (модули) и §3.6a (оболочка), `docs/SPEC-concierge-mail.md`, `modules/EXT1.md`.

---

## 1. Суть

Человек смотрит в наш календарь, а не в Google Calendar или Outlook. Там он видит свои встречи, принимает решения и
разговаривает с агентом, который делает координацию: ищет окна, переносит, учитывает дорогу, готовит черновики писем.

- Google Calendar и потом Outlook работают в фоне как **транспорт**. Копия событий хранится на домашнем сервере
  (homehub), у каждого человека отдельно, как почта в `concierge-mail`.
- **Наружу ничего не уходит без нажатия человека**: ответ организатору, новое событие или перенос в Google
  выполняются только кнопкой на событии. Агент только предлагает.
- Это отдельный модуль `calendar`. Вход в Google у него общий с почтой (одно согласие, права календаря добавляются
  дозапросом, §4).

## 2. Место в оболочке (§3.6a)

| Вид | Что даёт календарь |
|---|---|
| Приложение | `ui.page` `app: true, icon "📅", label "Календарь", window: true`: на ПК своё окно, в браузере и на телефоне весь центр. Виды «день», «неделя», «повестка». |
| Трей | `ui.header`: время ближайшей встречи (например `📅 10:00`) и красная точка, если в ближайшие 7 дней есть пересечение. Всплывающее окно: 3 ближайшие встречи и пересечения. Пусто, если служба не отвечает или встреч сегодня больше нет. Кнопок в трее нет. |
| Встраивание | (этап 2) режим чата `calendar` с просмотрщиком: календарь слева от чата «📅 Календарь». (этап 4) «Открыть с помощью» для `.ics`. |
| Служба | синхронизация провайдеров на homehub (systemd-таймер, как `concierge-mail-sync@`), поиск пересечений. |

## 3. Архитектура

```
Google Calendar API ─┐                        homehub, пользователь aiwb-<slug>
Microsoft Graph   ───┼─ слой провайдера ──► calsync ──► calendar.db (копия + свой слой)
ICS по ссылке     ───┘   (сменный)          ▲              │
                       токен: provider-accounts            ▼
                       (calendar.read/.write)   обработчик calendar ◄─ home-relay@<slug>
                                                                         │ (E2EE-конверт)
                                       сайт: home-relay, только передаёт (≤ 60 с), содержимого не видит
                                                                         │
                                 CO Web: приложение 📅, трей, просмотрщик рядом с чатом
```

### 3.1 Слой провайдера

Один интерфейс, каждая реализация в своём файле (`home/providers/google.py`, позже `graph.py`, `ics.py`):

| Операция | Google (этап 1) | Graph (этап 4) | ICS (этап 4) |
|---|---|---|---|
| `calendars()` | `calendarList.list` | `/me/calendars` | одна лента |
| `sync(cal, token, window?)` → изменения + новый токен | `events.list` с `syncToken`, `singleEvents=false`, `showDeleted=true`, все страницы; `410 Gone` → полная перечитка | `calendarView/delta` (нужно окно, отдаёт экземпляры) | весь файл, сравнение по `UID`+`SEQUENCE` |
| `respond(event, accepted\|declined\|tentative, comment?, newTime?)` | `events.patch` с полным массивом `attendees`, где изменён только свой ответ, проверка `etag` (If-Match), `sendUpdates=all` | `accept`/`decline`/`tentativelyAccept` (`proposedNewTime` — параметр ответа, `sendResponse=true`) | нет |
| `insert` / `move` / `delete` | `events.insert`/`patch`/`delete`, только если роль календаря и событие это позволяют | `/events` | нет |
| `propose_time(event, slot)` | нет в API; черновик письма организатору (через почту) | через `respond(..., newTime)`, если организатор разрешил | нет |
| `capabilities()` | запись, RSVP, предложение времени, окно синхронизации | то же | только чтение |

- Операции записи (`respond`, `insert`, `move`, `delete`) появляются на этапе 2 и вызываются **только** из
  обработчика нажатия человека (§6.3), никогда из задания агента.
- **Протокол синхронизации Google**: первая выборка — полный список без `timeMin/timeMax` (с ними `syncToken`
  несовместим), все страницы до `nextSyncToken`; изменения и новый токен сохраняются одной транзакцией, токен —
  только после последней страницы. `410 Gone` перестраивает **только копию провайдера**, свой слой остаётся и
  заново связывается по ключу и `iCalUID`. Глубина истории ограничивается при показе и в бэкапе, а не фильтром
  запроса.
- Повторяющиеся события храним как правило + исключения (`singleEvents=false`) и разворачиваем локально под окно
  вида (`dateutil.rrule` с `RDATE`/`EXDATE`, часовой пояс серии). Иначе бесконечная серия разворачивается в
  тысячи строк. Изменённый или отменённый экземпляр — отдельная строка с `recurringEventId` и
  `originalStartTime`; тесты на переход летнего времени и на изменение всей серии.
- Опрос раз в 5 минут, как у почты. Push-каналы Google (`events.watch`) требуют публичного https-адреса; это позже,
  если опроса не хватит.

### 3.2 Хранилище на homehub

Как у почты: службы работают под единым пользователем человека `aiwb-<slug>` (`provider-accounts`), каталог
`/srv/data/calendar/<slug>` (0700), токен из общего входа (§4).
Одна служба человека не читает календарь другого. Начинаем с SQLite, как почта.

- `calendars`: провайдер, аккаунт, id, название, цвет, роль доступа (`owner`/`writer`/`reader`/`freeBusyReader`),
  два отдельных флага «показывать» и «учитывать занятость», `sync_token`.
- `events` (копия провайдера, правится только синхронизацией): ключ провайдера, `ical_uid`, `etag`, статус
  (`confirmed`/`tentative`/`cancelled`), начало/конец в UTC и исходный часовой пояс; для «весь день» — даты
  без времени (конец не включается); правило повтора, `recurringEventId`, `originalStartTime`, занятость (`opaque`/`transparent`), организатор, участники и мой ответ, место, ссылка
  видеозвонка, описание, `updated`, `tainted` + правила read-guard.
- Свой слой (не смешивается с копией и не уходит провайдеру без нажатия): `proposals` (предложено агентом),
  `holds` (придержано), `decisions` (журнал нажатий: что, когда, что ушло провайдеру, ответ провайдера),
  `links` (событие ↔ цепочка почты, дело, человек из досье; этап 3), `travel` (этап 4).
- Удалённое у провайдера помечается `cancelled`, строка остаётся (история и связи не теряются).
- Бэкап: шифрованный бэкап на Drive человека (схема почты: `seal.py`, открытый ключ человека) — весь
  `calendar.db`. Новая синхронизация восстановит только то, что ещё есть у провайдера; удалённое там и история
  изменений есть только в нашей копии.

### 3.3 Безопасность

- Описание, место и названия чужих приглашений — внешний текст: проходят read-guard при записи, событие с
  подозрительным текстом помечается `tainted`. Агент получает такой текст обёрнутым как данные, действия по нему
  ждут явного «да».
- Внешние поля (описание, место, название, имена участников и календарей) — недоверенный текст всегда, даже
  без пометки read-guard: агенту — обёрнутыми как данные; на странице — только текст или очищенный HTML без
  внешних ресурсов, ссылки только `https:`/`mailto:`, открываются по нажатию.
- **Relay** — модуль `home-relay`: страница запечатывает запрос (ECDH P-256 + HKDF с солью
  `<env>|calendar|<id>` + AES-256-GCM), сайт держит конверт в очереди не дольше 60 с и содержимого не видит;
  обработчик календаря на homehub получает запрос от рабочего процесса человека `home-relay@<slug>`. Остаётся
  оговорка `home-relay`: тот, кто управляет кодом сайта, может выдать себя за страницу (закрывается в F9).
- **Изоляция решает homehub**, а не клиент: окружение человека рабочий процесс берёт из записи
  `provider-accounts`, обработчик назван в корневом `/etc/home-relay/modules.d/calendar.json`; от страницы
  приходит только имя модуля. Обработчик календаря сам сверяет, что календарь принадлежит
  `HOME_RELAY_ENV`, и иначе отвечает `not_bound`, как почта.
- **Что уходит в чат**: всё, что агент прочитал через действия календаря, попадает в протокол чата, журнал
  задания и контекст модели этого чата. Поэтому действия отдают минимум полей (время, название, занятость;
  описание — по отдельному запросу), а чат «📅 Календарь» работает на моделях, которые человек разрешил для своих
  данных.
- Права минимальные на каждом этапе: этап 1 — возможность `calendar.read` (у Google `calendar.readonly`),
  запись `calendar.write` (`calendar.events`) — когда человек включает этап 2. Токен у службы календаря суженный
  (`accounts.TokenSource(capabilities=[...])`): процесс календаря не держит почтовых прав, и наоборот. Право не
  отменяет роль календаря: возможность записи проверяется у каждого события.

## 4. Общий вход Google с почтой (готов: модуль `provider-accounts`)

Требование владельца (одно согласие на почту и календарь, права добавляются потом, токен свой у каждого и лежит
на homehub) выполнено в модуле `provider-accounts` (чат почты, 23.11). Календарь использует его так:

- **Возможности, а не права Google**: календарь просит `calendar.read` (этап 1) и `calendar.write` (этап 2);
  `accounts.py` переводит их в права провайдера (Google — `calendar.readonly` / `calendar.events`, Microsoft —
  `Calendars.Read` / `Calendars.ReadWrite`).
- **Добавить календарь к уже выданному входу**: `accountctl.py connect <slug> --want calendar.read`. Согласие
  просит весь набор (выданное + новое), потому что installed-app клиент не объединяет выдачи надёжно; почта всё это
  время работает на старом токене. Запущенная служба получает новые права после перезапуска.
- **Учётка**: `/etc/credstore.encrypted/account.<slug>.google.cred`, юнит календаря загружает её
  (`LoadCredentialEncrypted=account:...`) и получает токены только своих прав. Без выданной возможности служба
  отказывает до запроса и пишет, что нужно подключить календарь, — так её и показывает приложение.
- **Отключение**: `accountctl.py disconnect <slug> [--revoke]` снимает вход для всех модулей человека.
- **OAuth-клиент**: свой у каждой установки, статус In production (в Testing токены живут 7 дней), приложение не
  проверено Google: экран согласия с предупреждением, до 100 пользователей — для семьи достаточно.
- **Ещё не готово**: согласие с телефона (web-клиент с HTTPS-возвратом, этап 2c плана почты). До него член семьи
  подключает календарь с ПК.

## 5. Приложение 📅 (этап 1, только чтение)

- **Неделя** (по умолчанию на ПК): 7 колонок, полоса «весь день», линия «сейчас», цвет календаря. Пересечение
  занятых событий — красная рамка у обоих.
- **День** (по умолчанию на телефоне): одна колонка, свайп влево и вправо меняет день.
- **Повестка**: список на 14 дней по дням, пустые дни свёрнуты. На узком экране — третий вид рядом с «днём».
- **Событие**: время (и часовой пояс события, если он другой), место, ссылка видеозвонка, участники и их ответы,
  мой ответ, описание (обёрнутое, если `tainted`), «Открыть в Google».
  В версии 0.1 изменения делаются в Google; кнопки решения появляются на этапе 2.
- **Список календарей**: включить или скрыть в нашем виде; что скрыто, в пересечениях не участвует.
- **Состояние синхронизации**: «обновлено 2 мин назад»; если вход отключён — почему и как подключить.
- Часовой пояс — устройства; неделя с понедельника; язык — интерфейса CO.
- Всё рисует страница модуля в iframe (ext/1). Данные: `ui/relay.js` модуля `home-relay` →
  `HomeRelay(callOp, {env, module: 'calendar', op: 'cal_call'})` → своя операция `cal_call` → библиотека
  `relay.call` → обработчик на homehub (`{"op":"call","action":"range",...}`). Трей читает `cal_status`: плоский
  статус обработчика (до 20 значений: `next_start`, `next_title_short`, `conflicts`, `synced`, `bound`), без
  содержимого событий.
- Ограничения почтальона: обработчик отвечает по очереди, вызов до 30 с, ответ до 8 МБ, не больше 6 ожидающих
  вызовов на окружение по всем модулям. Поэтому страница просит одно окно вида за раз (неделя ≈ десятки событий) и
  не опрашивает чаще раза в минуту.

**Пересечение** (этап 1): два события в календарях с флагом «учитывать занятость», оба `opaque`, оба не
`cancelled`, мой ответ не `declined`, интервалы пересекаются. Занятое событие «весь день» (отпуск, поездка)
тоже участвует, но отмечается мягче; `transparent` не участвует. На этапе 4 к интервалу добавляется дорога.

## 6. Чат и действия агента (этап 2, F14b)

### 6.1 Чат внутри календаря

Используется уже существующий механизм ext/1: режим чата с просмотрщиком (`modes[].viewer`). Плитка 📅 открывает
постоянный чат человека «📅 Календарь» с включённым режимом `calendar`, а календарь стоит слева от чата
(`ui.panel`). На телефоне сетка и чат переключаются вкладками. Правила режима (`context/calendar.md`) описывают
агенту действия календаря и запреты. Собственный чат в iframe не делается.

Пользователь пишет «перенеси встречу X на вторник», «найди окно для звонка с Y на следующей неделе, утро не надо».
Агент отвечает предложениями на сетке и черновиками писем.

### 6.2 Действия приложения для агента (F14b)

Механизм F14b-1 уже есть: `provides.actions` `{op, description, args, outward}`, агент вызывает их через
`app_list` / `app_action` с правами человека своего окружения; `outward: true` агенту запрещено. Календарь
объявляет действия (все `outward: false`):

| Действие | Что делает | Наружу |
|---|---|---|
| `cal_list(from, to)` | события и свой слой за период | нет |
| `cal_free(from, to, duration, rules)` | свободные окна с учётом правил человека («утро не ставить», рабочие часы) | нет |
| `cal_propose(event \| move)` | предложение на сетке (пунктир) с объяснением | нет |
| `cal_hold(slot, reason, until)` | придержать окно (❓), пока идут переговоры; снимается само в `until` | нет |
| `cal_ask(event, options)` | кнопки решения на событии и карточка в «Waiting for you» | нет |
| `cal_drop(proposal \| hold)` | убрать своё предложение или hold | нет |

Действий записи у агента нет вовсе: `respond`, `insert`, `move` вызываются только нажатием человека.

**Действие агента через почтальона.** `app_action` вызывается на сайте без страницы, а `home-relay` принимает
только запечатанный конверт, ключ которого есть у страницы. Значит, нужен способ, которым задание агента
запечатывает запрос ключом рабочего процесса (клиент конверта в `toolbox`/`aiwb-tools` или прямой путь задания к
homehub). Открытым текстом через сайт действия не пойдут. У почты действий пока нет, так что календарь будет первым
пользователем. Решать вместе с чатом почты и чатом оболочки до этапа 2.

**Что ещё нужно от ядра** (в ext/1 нет): постоянный чат модуля, который открывается плиткой, с просмотрщиком без
документа (сейчас viewer привязан к пути `projects/...`); вкладки «сетка / чат» на телефоне; `coExt.badge`;
**подтверждение нажатием** — карточка в «Waiting for you» с одноразовым разрешением (заявлено как F14b-2, §6.3).

### 6.3 Состояния и решение на событии

| Состояние | Вид на сетке | Откуда |
|---|---|---|
| предложено | пунктирная рамка, полупрозрачно | `cal_propose` агента, приглашение из письма (этап 3) |
| придержано | ❓ на блоке | `cal_hold`; приглашение, на которое я ещё не ответил (`needsAction`) |
| подтверждено | обычный блок | событие провайдера, которое я принял или создал |

На событии кнопки: **Принять**, **Отклонить**, **Другое время** (агент ищет окна и готовит ответ). Нажатие —
`server.ops.user` `cal_decide` → relay → служба на homehub → провайдер (с правом `calendar.events`).

Сейчас `server.ops.user` не доказывает, что нажал человек. Нужен механизм ядра: **одноразовое разрешение**,
выданное по нажатию на конкретные аккаунт, событие, изменение и получателей уведомления, с коротким сроком;
агентский инструмент такое разрешение получить не может; повтор того же разрешения отвергается; служба
проверяет `etag` события и отказывает, если событие изменилось. Результат и ответ провайдера пишутся в
`decisions`. После таймаута служба сначала сверяет состояние у провайдера и только потом предлагает повтор
(иначе дубликат). Ошибка показывается на событии, повтор — снова нажатием. Письмо
организатору с окнами — черновик почты, отправляет человек.

## 7. Связь с почтой (этап 3, после приложения почты)

- Приглашения (`text/calendar`, `METHOD:REQUEST`/`CANCEL`) из писем: если Google уже добавил событие сам,
  связываем по `iCalUID`; иначе — предложение в календаре со ссылкой на письмо.
- Слоты из текста писем («могу во вторник в 10 или в среду после обеда») — разбор агентом почты, затем
  `cal_propose` с источником. Модули говорят через ядро (действия F14b), а не через файлы друг друга.
- У события — переписка и люди из досье; из события — «написать участникам» (черновик почты).
- Подготовка к встрече за час (SPEC почты §4): кто собеседник, история переписки, что обещано.

## 8. Outlook, ICS и дорога (этап 4)

- **Outlook** (Microsoft Graph, личный аккаунт): второй провайдер того же интерфейса, свой вход Microsoft
  (тот же принцип: токен у человека на homehub). Сейчас не реализуется, интерфейс провайдера под него готов.
- **Подписки ICS** по ссылке (школа, спорт, праздники): только чтение, опрос раз в час.
- **«Открыть с помощью»** для `.ics` из чата: импорт как предложение.
- **Время в пути**: место события → координаты (геокодер OSM), маршрут от предыдущего места или от дома (места
  `geo-presence`, если человек разрешил); блок «дорога» перед событием, пересечения с учётом дороги, push «пора
  выходить». Способ передвижения — по правилу человека (машина, велосипед, транспорт).

## 9. Семья

Каждому члену семьи — свой экземпляр: свой вход Google, свой каталог и пользователь на homehub, свой чат
«📅 Календарь». Общий семейный вид (кто когда занят) — только с согласия каждого и только «занят/свободен» без
подробностей; это открытый вопрос (§11).

## 11. Открытые вопросы

1. Сколько истории тянуть: предложение — год назад и всё вперёд, старое по запросу.
2. Придержанное окно (❓): только у нас или по нажатию ещё и событием «Hold» в Google, чтобы его видели другие?
3. Общий семейный вид «занят/свободен»: нужен ли и кому.
4. Правила человека для окон (рабочие часы, «утро не ставить», буфер между встречами): задаются словами в чате
   и видны списком в настройках модуля — подтвердить.
5. Push-уведомления о встречах: свои напоминания календаря или оставить напоминания Google на телефоне.

## 12. Этапы

0. **Предварительные задачи (не календарь)**: общий вход Google (`provider-accounts`) и общий почтальон
   (`home-relay`) — готовы 23.11. Для этапа 2 ещё нужны: конверт для действий агента (§6.2), карточка с
   одноразовым разрешением (F14b-2), чат модуля с просмотрщиком без документа.
1. **0.1 — только чтение**: Google → homehub, приложение 📅 (неделя, день, повестка, телефон), трей (ближайшая
   встреча, точка пересечения). Критерии приёмки: отзыв доступа даёт понятное состояние, `410` перестраивает
   копию без потери своего слоя, повторы и переход летнего времени показываются верно, недоступный homehub —
   «нет связи» и последнее время обновления, второй человек не видит чужой календарь ни через страницу, ни через
   агента.
2. **0.2 — чат и действия (F14b)**: режим чата с просмотрщиком, действия агента, состояния на сетке, кнопки
   решения, запись в Google по нажатию (`calendar.events` дозапросом).
3. **0.3 — связь с почтой**: приглашения и слоты из писем, связь событий с цепочками и досье, черновики ответов.
4. **0.4 — Outlook и ICS, дорога**: провайдер Graph, подписки ICS, `.ics` «Открыть с помощью», время в пути.
